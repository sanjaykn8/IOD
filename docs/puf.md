# PUF Simulation and Fuzzy Extractor

## SRAM-PUF simulation (`puf::sram_puf`)

Real SRAM PUFs exploit manufacturing variation: uninitialized SRAM cells
settle into a 0 or 1 state at power-up that is device-specific and
mostly (not perfectly) stable across power cycles. This project
simulates that with:

- A fixed, per-device **golden pattern** (992 bytes / 7936 bits),
  generated once from local device entropy and never persisted in the
  GCS-side database (see "the two-table split" below).
- A **noise model**: each `read()` independently flips each bit with
  probability `bit_flip_prob` (default 5%, within the 2-15% range
  reported for real SRAM PUFs across temperature/voltage corners).

## Fuzzy extractor (`puf::fuzzy_extractor`) — code-offset construction

Standard Dodis-Ostrovsky-Reyzin-Smith construction:

```
Gen(R):    C ← random 256-bit message
           codeword = repeat_encode(C)         // REPEAT=31 copies per bit
           W = R XOR codeword                  // helper data (safe to store)
           seed = SHAKE256(C)
           output (W, seed)

Rep(R', W): masked = R' XOR W = codeword XOR (R XOR R')
            C' = majority_vote_decode(masked)
            output SHAKE256(C')                // == seed iff decoding succeeded
```

**Error-correcting code**: a binary repetition code (REPEAT=31,
majority-vote decoding), not a BCH/Reed-Solomon code. This is a
deliberate simplification, prioritizing an implementation that is easy
to verify correct by inspection over one with an optimal code rate. The
trade-off: correcting a given noise level requires roughly `31x` more
raw PUF bits than a well-tuned BCH code would need for the same
reliability — irrelevant for a simulator, since "raw PUF bits" are just
simulated array elements here, not physical silicon area.

### Reliability, actually computed (not assumed)

Two independent noisy readings of the same simulated chip (each with
independent per-bit flip probability `q` relative to the invisible
golden pattern) differ from each other with probability `p = 2q(1-q)`.
For a REPEAT=`n` repetition code, a block decodes incorrectly if more
than `n/2` of its `n` bits differ, which is a binomial tail — computed
exactly (not estimated) below for several `(q, REPEAT)` combinations:

| Simulated noise `q` | Effective inter-reading diff `p` | REPEAT | Per-block failure | Per-attempt failure (256 blocks) |
|---|---|---|---|---|
| 2% | 3.9% | 31 | 5.3×10⁻¹⁵ | 1.4×10⁻¹² |
| **5% (project default)** | **9.5%** | **31** | **3.3×10⁻⁹** | **8.3×10⁻⁷** |
| 8% | 14.7% | 31 | 1.6×10⁻⁶ | 4.0×10⁻⁴ |
| 8% | 14.7% | 45 | 1.1×10⁻⁸ | 2.7×10⁻⁶ |
| 12% | 21.1% | 45 | 8.6×10⁻⁶ | 2.2×10⁻³ |
| 15% | 25.5% | 61 | 2.0×10⁻⁵ | 5.1×10⁻³ |

This table was generated by direct binomial-tail computation (see the
Python one-liner in this repo's session notes / reproducible via
`scipy`-free `math.comb`), not by running the actual Rust code
statistically — the Rust unit test
(`fuzzy_extractor::tests::reconstructs_identical_seed_despite_noise`)
then separately EMPIRICALLY confirms 25 consecutive successful
reconstructions at the default 5% noise level, consistent with the
8.3×10⁻⁷ theoretical per-attempt failure probability above.

**This is not "zero failure probability."** No real fuzzy extractor has
that. It is small enough to be a non-issue for a bounded research
simulation, while remaining honest that a residual failure rate exists
— exactly the kind of claim precision the project brief requires
("do not claim the entire system is mathematically proven secure").

### A real bug this reliability analysis caught

The first parameter choice (REPEAT=15) was NOT sufficiently reliable at
the noise level used in a 25-trial test loop and produced a real,
reproducible test failure during development. Root-caused as a
reliability-margin problem (not a logic bug in the encode/decode
functions), fixed by increasing REPEAT to 31 with the table above
computed and checked BEFORE re-running the test, rather than by
weakening the test.

## Challenge-response PUF (`puf::crp`)

`PUF(D, C) -> r` is modeled as `SHAKE256(golden_pattern || challenge)` —
deterministic (noise-free) for a fixed challenge. This is a documented
simplification relative to the seed-reconstruction path above: the
noisy-reconstruction problem is already demonstrated there, and
re-applying full fuzzy extraction to the CRP path as well would
duplicate the same mechanism without additional pedagogical value in
this prototype. A production system would apply the same code-offset
reconciliation to CRP responses too.

GCS stores only the **reference response** `(challenge, r_ref)` per
drone, captured over the trusted enrollment channel — never the raw PUF
golden pattern, never a reconstructed seed. See `docs/security-review.md`
for the full accounting of what GCS does and does not hold.

## The two-table persistence split

- `gcs_state` (SQLite): what a real GCS server would legitimately
  persist — public keys, metadata, CRP *reference responses*, Merkle
  state, the PID pool. No private keys, no PUF golden patterns.
- `drones_local` (SQLite): what would physically live on ONE drone's own
  flash storage in a real deployment — private keys, the simulated PUF
  golden pattern, cached witness/root/version. This distinction is
  structural (two different Rust snapshot types, two different tables),
  not just a comment — see `storage::snapshots` module docs.
